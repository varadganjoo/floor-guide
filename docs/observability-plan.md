# Application and agent observability

Date: 23 November 2026  
Status: Local logging and inspection implemented. External exports remain configuration-controlled and have not been live-verified.  
Parent: [Document chat design](document-chat-plan.md)

## Purpose and tools

The local frontend `/observability` dashboard implements Metrics, Traces and Logs views. `GET /api/observability/summary` supplies time-windowed aggregates with sample counts and usage coverage; run/detail endpoints support filtering and bounded pagination. Per-query total/input/output token counts, execution waterfalls, saved transcripts, references and correlated HTTP timings are available. `GET /api/observability/logs` reads SQLite actions/HTTP records or bounded rotating JSON diagnostics, identifying the source. Unknown usage remains unknown. Export delivery/link fields, persisted proxy duration and token subfields absent from stored events are displayed as unavailable. See the README for exact windows, populations and limits.

An operator should be able to open a conversation, select a question, read the exact response delivered to the supervisor, and inspect the actions and time spent producing it. This covers the browser, Next.js proxy, FastAPI, database, LangGraph, document tools and OpenAI calls.

Use three complementary pieces:

1. **SQLite run ledger:** durable local record of turns, execution segments, action events and request measurements. Questions and answers remain in the existing message tables. This is the source for the local inspector and works without a telemetry-service account.
2. **Structured JSON logs:** Python standard logging and structured Next.js server logs for request completion, errors, imports, persistence, retries and operational diagnostics. Use bounded fields and rotating local files or stdout captured by the deployment runtime.
3. **LangSmith traces:** configured integration for LangChain/LangGraph nodes, model/tool calls and custom Decisions spans. The LangSmith interface provides the agent execution tree. Export stays optional; a local session record must not depend on the export succeeding.

For this prototype, correlate application logs and timings with agent traces using explicit IDs. Do not claim one automatically instrumented browser-to-model distributed trace: Next.js/browser measurements are linked records, while LangSmith holds the agent trace tree. An OpenTelemetry collector, a metrics server and another dashboard service are unnecessary for the initial version.

## Identity and session management

| Identifier | Lifetime and use |
| --- | --- |
| `conversation_id` / LangGraph `thread_id` | Stable agent session, persisted in SQLite. Survives reload, backend restart, clarification and subsequent questions. |
| `turn_id` | One logical question through its clarification rounds, retries and final answer. Stable until completed, cancelled or failed. |
| `execution_id` | One active graph invocation. Resuming after human input creates a new execution linked to the same turn and its previous execution. |
| `request_id` | One backend HTTP attempt, generated by the server and returned as `X-Request-ID`, including on errors. A transport retry receives a new request ID. |
| `operation_id` | Client idempotency key for one logical send/resume/cancel operation. Stable across transport retries, distinct from `request_id`. |
| `proxy_request_id` | Validated, bounded identifier linking a Next.js proxy request to its FastAPI request record. Never use arbitrary incoming text as log structure. |
| `trace_id`, `span_id`, `parent_span_id` | Trace identity for the current execution and its children. Keep local identifiers when external tracing is disabled; store external LangSmith IDs separately when they differ. |
| Provider request/response IDs | Actual identifiers returned by OpenAI for each attempt, when available. Useful for support and distinguishing retries. |

A conversation is the agent session. Do not create a new one merely because an HTTP request ended or the agent paused for clarification. There is no additional user-identity or cross-conversation memory layer in this unauthenticated local prototype.

Pass the conversation/thread ID on every LangSmith root and child run, together with turn and execution metadata. Each initial invocation and resume gets a new trace segment; group those segments by turn and conversation rather than leaving one span open across hours of human waiting. Reject a resume whose conversation, turn, interrupt and version do not match the stored checkpoint.

Carry context through thread-pool execution and callbacks explicitly, using request-local context rather than global mutable identifiers. Concurrent sessions must never share trace tags, messages or token totals accidentally.

## What is captured

| Stage | Recorded information |
| --- | --- |
| UI submission and rendering | Operation ID, matching server request ID, browser elapsed time, displayed outcome and frontend error category. No second copy of message content in client telemetry. |
| Next.js proxy | Proxy/request correlation, route template, method, status, upstream duration and transport errors. No credentials or raw request bodies. |
| FastAPI request | Start/end timestamps, monotonic duration, status, route template, conversation/turn IDs and sanitized error details. Include non-agent endpoints such as conversation/history reads. |
| Database | Operation label such as `load_history` or `save_answer`, duration, outcome and row counts where useful. Do not log SQL parameter values or the complete database contents. |
| History selection | Candidate and selected turn IDs, returned relevance probabilities, threshold/budget configuration, retained token counts, Decisions duration and usage. Record when the call was skipped because no history needed filtering. |
| Main agent call | Configured and returned model ID, effective reasoning setting, prompt/app version, provider IDs, input/output token usage and duration. Record the action/tool call it returned. |
| Document search | Tool-call ID, validated arguments, chosen topic/document IDs, source/section IDs, scores, result count, evidence size, no-results outcome, attempt count and elapsed time. |
| Argument correction and retries | Error class, sanitized explanation, retryability, attempt number, backoff duration and final outcome. A retry is an attempt, not an additional logical user question. |
| Clarification | The stored clarification question and human reply, interrupt ID, pause/resume/cancel events, waiting duration and counters. |
| Validation and persistence | Answer-schema and citation checks, source IDs, success/failure, and time to commit the answer and references. |
| Completed turn | Exact user question and final displayed answer through message IDs, references, selected topics, status, active/wall/wait timings, usage and trace links. Retain refusals and failures too. |
| Document loading/application startup | File/catalog version, parse count, unavailable sources, startup timing and sanitized errors. No document body dump. |

The action timeline can read, for example: `history_selected → search_requested → search_completed → clarification_requested → paused → resumed → search_completed → answer_validated → completed`. Distinguish the main agent's actions from the Decisions API's history-filter results. Capture short explicit action descriptions and structured outcomes; do not request or store private chain-of-thought.

The inspector must distinguish the provider's raw output, an unvalidated draft, a clarification prompt and the final answer actually displayed. Local full-content model debugging can be an explicit development setting; the final user-visible transcript is always available through the ordinary message store.

## Latency definitions

All duration fields use explicit `_ms` units. Use monotonic clocks for durations within a running process (`performance.now()` in the browser and a monotonic Python clock on the server). Record UTC timestamps for ordering and correlation across processes/restarts; display them in the viewer's timezone. Do not subtract unrelated browser/server clock readings.

| Metric | Definition |
| --- | --- |
| `client_response_ms` | Browser elapsed time from accepting send/resume to painting the returned validated answer, clarification prompt or error. Measured for one request; the outcome is recorded alongside it. |
| `proxy_ms` | Next.js proxy's own request/upstream duration. It overlaps backend work; do not add it to backend time to invent an end-to-end total. |
| `server_request_ms` | FastAPI elapsed time from accepting the request to finishing the response. Includes request validation, database work and any agent invocation. |
| `agent_execution_ms` | One active graph invocation, including provider waits, tool work, retry backoff, validation and orchestration overhead. No human idle interval. |
| `agent_active_ms` | Sum of the non-overlapping execution durations for a turn across initial invocation and resumes. Nested spans are not added again. |
| `provider_ms`, `tool_ms`, `db_ms`, `validation_ms` | Span durations for diagnosis. Show overlap in the timeline; their sum need not equal overall duration. |
| `human_wait_ms` | Sum of persisted pause-to-accepted-resume/cancel intervals. Compute across restart from stored UTC timestamps and flag clock anomalies; do not include it in provider/agent processing latency. |
| `turn_elapsed_ms` | Wall-clock time from original question acceptance to terminal outcome, including human waits and time between requests. Mark clock anomalies instead of displaying negative durations. |

For an ordinary one-request answer, `client_response_ms` is the application latency the supervisor experiences. A clarification request has its own quick response time; the eventual answer has a separate resume response time and an overall turn duration. Browser measurements are advisory and cannot be reconstructed reliably after a closed tab; missing measurements remain null. Backend measurements are authoritative for server processing.

The first release does not stream answer tokens, so time-to-first-token is not a user-visible metric yet. Add it only when streaming exists, with a precise definition.

## Storage and inspection

Extend the planned application database rather than introducing another logging database:

- Extend `conversation_runs` with start/completion timestamps, terminal outcome, question/answer message IDs, accumulated active/wait duration, model configuration, prompt/app version, usage summary and observation completeness.
- Add `run_events`: stable event ID, conversation/turn/execution IDs, event type, local/external trace and span IDs, parent ID, timestamp, duration, attempt number, outcome and a bounded structured payload.
- Add `request_observations`: request/proxy/operation IDs, linked turn/execution, route template, HTTP outcome, server/proxy/browser timing fields and sanitized error category. Browser reports update the matching record idempotently after server completion.
- Index conversation/turn/time, request ID and event type. Join questions and answers from `messages`; do not replicate the full transcript in each event row.
- Assign event identities from logical execution/tool/attempt identities so checkpoint replay does not duplicate the same action event. A real repeated provider attempt receives its own attempt event and usage record.

Give the developer a small read-only **Run inspector** route in the local app:

1. Session list with recent activity, turn counts and outcomes.
2. Per-session questions and answers, including clarification exchanges.
3. Per-turn timeline with actions, chosen topics, source references, retry/error details, usage and timing breakdown.
4. A trace link when exported to LangSmith; show `disabled`, `pending`, `sent` or `failed` instead of a misleading broken link when export is unavailable.
5. A summary of p50/p95 client/server/agent latency, throughput, completed/failed/waiting turns, tool no-results rate, clarification rate, provider retries and token totals. Each aggregate shows its time window, eligible sample count and outcome filter. Waiting turns are not labelled completed or failed. Keep high-cardinality IDs in events, not metric dimensions.

Proposed endpoints: `GET /api/observability/runs`, `GET /api/observability/runs/{turn_id}`, and `GET /api/observability/summary`, plus a bounded `POST /api/telemetry/client` for timing/error reports linked to a known request ID. Paginate event/message lists. Validate client-provided timings and rate-limit reports; do not trust them for billing or server SLOs. This inspector shares the prototype's local-only access boundary; remote/shared deployment needs access control before exposing transcripts.

## Model settings and usage accounting

Every answering-agent Responses request uses `model="gpt-6-luna"` and `reasoning={"effort":"none"}`. This includes action selection, structured final answers, repairs and resumes. The adapter must preserve that setting across tool binding and retry calls. There is no automatic escalation to a thinking level.

The Decisions endpoint is a separate history-selection API whose documented schema has no reasoning-effort field. Record `endpoint=decisions` and that the setting is not applicable there. Do not send `reasoning` to Decisions or advertise a nonexistent configuration switch.

Record actual provider token fields for every completed call/attempt: input, output, cached-input and reasoning tokens when returned. Preserve null when unavailable; a configured effort of `none` must not be substituted for measured zero tokens. Do not add reasoning tokens again when they are already included in output usage, or cached input again when included in input totals. An attempt that fails before returning usage can have an unknown cost.

Optional estimated cost uses Decimal arithmetic and a dated model/endpoint price schedule, with the applicable cached/uncached and processing-tier rules. Label estimates, currency, price version and unknown coverage. The Decisions call and failed/retried provider attempts belong in the same turn's cost view. Do not infer real savings from reduced prompt size alone.

## Content, export and reliability

Store questions, clarification exchanges and answers locally as required for conversation history and run inspection. JSON operational logs default to IDs, counts, timings and error categories. Never log `.env` values, authorization headers, cookies or complete exception objects that may embed request bodies. Sanitize metadata and error text as well as span inputs/outputs.

LangSmith export is controlled by backend configuration. With no account/key, local observation remains available. In metadata-only export mode, hide model/tool inputs and outputs on both root and child spans, and filter free-text metadata such as search queries. Include only explicitly allowed identifiers, durations, counts, model settings and error categories. A separate explicit content-export setting can send sanitized questions, answers and necessary excerpts for development debugging. Enabling tracing must not accidentally enable full transcript export.

Use the documented `LANGSMITH_TRACING` and `LANGSMITH_API_KEY` settings. Resolve project/agent/environment configuration against the installed SDK's current docs during implementation; do not assume an obsolete integration configuration. No trace exports are enabled by writing this plan.

Start with all local turns/events recorded for the prototype. Rotate logs with a finite size and backup count. Retain conversation history until an explicit deletion policy is introduced; do not silently purge it as log cleanup. Limit diagnostic event payload sizes and document the local diagnostics retention window. Hosted trace retention and account costs depend on the configured service. Do not require a new observability account simply to run the chat.

External export is best-effort and bounded: use nonblocking batched delivery, a finite queue and shutdown flush. Record dropped/export-failed counts locally and show degraded observation status. Do not retry a whole agent turn because its trace export failed. Keep minimum run identity and final observation linkage in the answer transaction; a failed chat-persistence transaction still follows the ordinary explicit failure path.

## Acceptance checks

- A normal question is visible with the exact displayed answer, model setting, selected topics, source references and linked execution/request IDs.
- Every model/tool/Decisions call has the right parent and conversation/turn metadata; direct SDK calls do not disappear from the timeline.
- Two simultaneous conversations have isolated IDs, messages, timings and usage totals.
- A clarification pause/restart/resume stays in one session/turn, produces linked execution segments, and separates human waiting from processing time.
- Validation corrections and transient retries are visible as individual attempts; idempotent request replay does not duplicate a logical turn or its action events.
- Browser, proxy and backend timings are named distinctly and overlap correctly. A slow provider and an injected slow database operation are visible in the correct spans. No total sums nested overlapping spans.
- Completed/failed/waiting counts, percentiles, empty-window behavior and token totals are checked with known fixtures, including missing usage and missing browser reports.
- All serialized Responses requests carry effort `none`; tool binding, schema repair, retries and resume do not reintroduce a default reasoning level. Decisions receives only supported fields.
- Sentinel credentials and document text do not appear in metadata-only export, including child spans, errors and metadata. Local transcript visibility still works.
- Disabling tracing, removing its key, filling the export queue or simulating an export outage does not break a successful chat response. Export loss is visible locally.
- Reopening a recorded run does not invoke the LLM again. Inspector lists and event bodies remain paginated/bounded.
